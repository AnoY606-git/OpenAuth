# Формат резервной копии Open Auth, версия 1

Файл содержит полный снимок хранилища. Его можно восстановить без сервера Open Auth: нужны файл и пароль либо PIN. Сжатие не применяется. Все целые числа в бинарном контейнере имеют порядок байтов big-endian. UUID записывается как старшие 64 бита, затем младшие 64 бита. Все размеры приведены в байтах; смещения отсчитываются от начала файла.

## Криптографические параметры

Пароль нормализуется Unicode NFC и кодируется UTF-8, без удаления пробелов и изменения регистра. После NFC требуется не менее 12 кодовых точек и не более 1024 байт UTF-8. Некорректные UTF-16 последовательности не принимаются. PIN состоит из 8–128 ASCII-цифр; ведущие нули сохраняются. Пароль и PIN — разные типы учётных данных.

Ключ шифрования ключа копии (KEK): Argon2id версии 1.3 (число 0x13), память 65536 КиБ, 3 прохода, 4 линии, выход 32 байта, случайная соль 16 байт. Другие параметры в версии 1 запрещены: читатель обязан проверить профиль до запуска Argon2. Argon2 secret и additional data отсутствуют.

Ключ данных копии (DEK) — независимые случайные 32 байта. KEK шифрует DEK алгоритмом AES-256-GCM с nonce 12 байт и тегом 16 байт. DEK шифрует UTF-8 JSON тем же алгоритмом. Ciphertext в каждом поле непосредственно предшествует своему тегу. Никакой открытый текст не выдаётся до проверки тега.

## Бинарная раскладка

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 8 | ASCII `OABACKUP` |
| 8 | 2 | Версия контейнера: 1 |
| 10 | 1 | Тип: 1 — пароль, 2 — PIN |
| 11 | 1 | KDF: 1 — Argon2id |
| 12 | 4 | Версия Argon2: 19 |
| 16 | 4 | Память Argon2 в КиБ: 65536 |
| 20 | 4 | Проходы: 3 |
| 24 | 4 | Линии: 4 |
| 28 | 16 | Соль Argon2 |
| 44 | 16 | Случайный идентификатор поколения |
| 60 | 12 | Nonce обёртки DEK |
| 72 | 48 | Обёртка: зашифрованный DEK 32 + тег 16 |
| 120 | 16 | Идентификатор снимка |
| 136 | 8 | Время создания, signed Unix seconds, ≥ 0 |
| 144 | 12 | Свежий случайный nonce полезной нагрузки |
| 156 | 4 | Длина открытого JSON, signed integer, 0…8388608 |
| 160 | N | Зашифрованный JSON той же длины N |
| 160 + N | 16 | Тег полезной нагрузки |

Длина файла строго равна `176 + N`; хвостовые байты запрещены. Предельный размер файла — 16777216 байт; ограничение JSON строже. До KDF проверяются полный размер, фиксированные поля, профиль KDF, длина JSON, время и точное совпадение длины файла.

AAD обёртки: ASCII-байты `OpenAuth/backup/wrapper/v1` с последующим единственным нулевым байтом, затем исходные байты файла `[0,72)`.

AAD полезной нагрузки: ASCII-байты `OpenAuth/backup/payload/v1` с последующим единственным нулевым байтом, затем исходные байты файла `[0,160)`. Следовательно, поколение, обёртка, идентификатор и время снимка, nonce и длина защищены тегом полезной нагрузки. При чтении AAD берётся из исходного файла, без повторной сериализации полей.

Заголовок поколения `[0,72)` и обёртка `[72,120)` остаются неизменными для последовательных снимков одного поколения. Каждое шифрование снимка получает новый случайный 96-битный nonce от системного SecureRandom. Для q снимков одного ключа вероятность случайной коллизии ограничена примерно q(q−1)/2^97; приложение должно создавать новое поколение до 2^32 снимков. Это вероятностная гарантия, а не глобальный счётчик nonce. При изменении пароля или восстановлении на другом устройстве создаются новый DEK, соль и полная копия. Старое поколение служит только для чтения старых файлов.

## JSON снимка

Кодировка UTF-8 строго проверяется. Объект верхнего уровня содержит обязательные поля `schemaVersion` (1 или 2), `revision` (неотрицательное signed 64-bit), `entries` (массив до 10000 записей), `groups` (массив до 10000 групп). Неизвестные поля, некорректные типы, избыточная вложенность и нарушения инвариантов модели отвергаются. Максимальная вложенность JSON — 8 контейнеров. Числа сериализуются десятичными JSON-числами, без потери точности 64-битных значений. Лимиты массивов проверяются при чтении, до материализации лишнего элемента.

Запись содержит `id` (UUID в стандартной строковой форме), `issuer`, `accountName`, `secret` (стандартный Base64 RFC 4648 с padding), `type` (`TOTP` или `HOTP`), `algorithm` (`SHA1`, `SHA256`, `SHA512`), `digits` (6 или 8), `periodSeconds` (15…120), `nextCounter` (0…9223372036854775807), `groupId` (UUID либо null), `favorite` (boolean), `sortIndex` (signed 64-bit). Декодированный секрет имеет 10…128 байт. HOTP поддерживает SHA1. Группа содержит `id` и `name`. Идентификаторы записей и групп уникальны; непустой `groupId` ссылается на существующую группу.

Схема 2 добавляет `hotpCounterFloors`: до 20000 объектов с полями `fingerprint` (64 строчные шестнадцатеричные цифры SHA-256) и `nextCounter` (1…9223372036854775807). Отпечаток равен SHA-256 от ASCII `OpenAuth/HOTP/counter-floor/v1`, единственного нулевого байта и байтов OTP-секрета. Он не зависит от метаданных, длины кода, периода и текущего типа карточки. Отпечатки уникальны; максимум счётчиков сохраняется после удаления карточек, смены их типа/длины и обоих режимов восстановления. История хранится только внутри зашифрованного JSON и не содержит исходных удалённых секретов. При достижении предела операция отказывается, а не вытесняет старую историю. Полностью удалять её автоматически небезопасно.

Читатель поддерживает старую схему 1 без истории. При работе со старым vault история строится из доступных HOTP-счётчиков и сохраняется со следующей записью. После появления ненулевой истории используется схема 2. До этого момента схема 1 остаётся допустимой; пустое поле истории не сериализуется. Восстановить использование, отсутствующее и в текущем хранилище, и в копии, невозможно.

**Совместимость:** версия бинарного `.oab` и профиль шифрования остаются 1; меняется схема зашифрованного JSON. Старые копии открываются новой версией приложения. OpenAuth 1.0.0 не читает схему 2 и безопасно отклонит новые копии с историей; для них нужна обновлённая версия. Откат APK после обновления vault до схемы 2 также не поддерживается. Копии с более чем 10000 группами отвергаются новым лимитом.

`SnapshotJsonCodec` кодирует только перечисленные данные: пароль, KEK и DEK туда не включаются. Этот же кодек предназначен для данных локального зашифрованного хранилища.

## Локальное состояние поколения

`BackupGeneration.exportLocalState()` возвращает новую чувствительную копию ровно 160 байт: ASCII `OALOCAL1` (8), неизменный заголовок поколения (72), обёртка (48), **открытый DEK** (32). `BackupGeneration.importLocalState(bytes)` проверяет длину и заголовок, копирует данные и не сохраняет ссылку на входной массив. Этот внутренний формат не является переносимой резервной копией. Его разрешено хранить исключительно внутри шифротекста локального vault, защищённого Android Keystore; отдельно в preferences, Bundle, логах и файлах сохранять нельзя. Вызывающий код обязан обнулить экспортированный массив после шифрования. В импортированном состоянии предполагается уже проверенная аутентичность локального vault; без неё его применять нельзя.

`close()` у поколения и учётных данных обнуляет принадлежащие им байтовые массивы и запрещает дальнейшее использование. KEK и временные копии DEK обнуляются в `finally`. JVM, нормализация строк, JSON и криптографический провайдер могут создавать дополнительные копии; абсолютное удаление всех следов из управляемой памяти не гарантируется.

Нарушения структуры, неподдерживаемый заголовок и превышение лимитов отклоняются до KDF с `INVALID_FORMAT` либо `LIMIT_EXCEEDED`. Для корректно сформированного контейнера неверные учётные данные или несовпадение AEAD-тега возвращают общую ошибку `AUTHENTICATION_FAILED`. Исключения кодека содержат только категорию ошибки, без исходных секретов, JSON и причин исключений парсера.
